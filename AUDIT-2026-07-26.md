## 1. Bottom line

The core is well built for a small studio: uploads go straight from the browser to Cloudflare R2 (big files never touch the server), auth is sensible, the montage webhook is written defensively, and the new timeline/Character Build features are scoped so a client can only ever touch their own media. Nothing I found deletes client photos behind your back.

**But** your stated bar is "we cannot lose client pictures," and against *that* bar there is one real gap: **there is no independent backup of the R2 bucket, and deletes are unrecoverable.** R2 being durable is not the same as being backed up. This is the single most important thing to fix, and most of it is Cloudflare/Supabase configuration you do once — not code.

## 2. Data safety & backup (your #1 concern)

### P0-1 — No independent backup of client media
Every client photo and video lives in **one** Cloudflare R2 bucket. Cloudflare markets R2 as highly durable, but a single bucket does not protect you from the realistic loss events: a leaked/rotated credential, an accidental lifecycle or bulk-delete, a bucket misconfiguration, or a bug. If that bucket goes, the pictures are gone.
**Do:**
- Turn on **R2 object versioning** (Cloudflare dashboard → bucket → Settings). With versioning, an overwrite or delete keeps the prior version and is recoverable. This alone closes most of the risk and requires **no code**.
- Add a **second copy**: either R2 → another R2 bucket in a different account, R2 → Backblaze B2/AWS S3 on a nightly schedule (rclone/cron), or Cloudflare's bucket-to-bucket replication if available on your plan. Off-account is best (protects against account compromise).
- Consider **object lock / retention** on the client-upload prefix so nothing can be deleted for N days even by an admin action.

### P0-2 — Hard deletes are irreversible (no versioning today)
`lib/r2.js deleteFile()` issues a real `DeleteObject`. It's called by the admin "Empty Trash" (`deleteMany`) and admin single `delete` in `lib/mediaOrganize.js`, and by the Character retake path. Without versioning (P0-1) these are permanent with no undo.
**Do:** enabling R2 versioning (P0-1) makes these recoverable. Optionally change admin deletes to a **soft-delete** (move the object to a `deleted/` prefix with a 30–90 day lifecycle-expiry) instead of an immediate `DeleteObject`, so "Empty Trash" is never a live grenade. This is a small code change I can make on request.

### P0-3 — The Supabase DB is the only index to R2, and R2 keys are opaque UUIDs
Object keys are `studio/{clientId}/{uuid}.{ext}` — there is no client name or original filename in the key. The mapping "which object is which client's photo #3" lives **only** in the `studio_media` table. If that table is lost or corrupted, the objects still exist but are effectively unfindable.
**Do:** confirm **Supabase Point-in-Time-Recovery / daily backups** are enabled for the project (plan-dependent — verify in the Supabase dashboard). Optionally write a periodic **manifest** (a JSON/CSV of id→key→client→filename) into R2 so the index itself is backed up alongside the media.

### P1-4 — Upload is two steps; a half-finished upload silently loses the file from view
The flow is: browser `PUT`s the file to R2 via a presigned URL, then calls `/api/portal/confirm` (or `/api/portal/character`) to insert the `studio_media` row. If the PUT succeeds but the confirm call fails (dropped connection, server error), **the file is physically in R2 but has no DB row** — invisible to both client and studio, and the client sees "failed" and may not retry. It's not destroyed, but from the user's view it's lost.
**Do (any of):**
- Retry the confirm call on failure (currently `uploadOne`/`putBlob` mark the item errored but don't retry the confirm step).
- Add a **reconciliation sweep** (admin button or cron): list R2 under `studio/{clientId}/`, find objects with no matching `studio_media.r2_key`, and either re-attach or report them. This doubles as a safety net for P0-3.
- Surface partial failures more loudly in the client UI ("1 photo didn't finish saving — tap to retry").

### P1-5 — Delivered montages can vanish after ~30 days if the R2 archive step fails
`app/api/webhooks/creatomate/route.js` copies the finished MP4 into R2, but it's best-effort with `maxDuration = 60s`. A large final render can exceed the download+upload window on Vercel, leaving `r2_key = null` and the montage living **only** on Creatomate's temporary hosting (~30 days per their docs). After that it's gone.
**Do:** add a **re-archive job** — a cron (or reuse `montage/sync`) that finds `studio_montages` rows with `r2_key IS NULL` and `status='ready'` and retries the copy; alert if any stay unarchived. Show an "not yet archived" badge in admin (you already store the flag).

### P2-6 — No server-side file-type/size limits on client uploads
`confirm` trusts the client-supplied `contentType`; a client could store non-media in their own folder. Low risk (it's their own space, admin-only delete), but worth a basic allowlist + max size to avoid abuse/cost.

**Already fixed tonight:** the Character **retake** path used to delete the old shot *before* saving the new one — a failed save could empty a slot. It now saves the new shot first, then removes the old. (Committed.)

## 3. Security & privacy

**Solid:**
- Portal sessions are HMAC-signed, HttpOnly, Secure, SameSite=Lax, 30-day, with `timingSafeEqual` (`lib/session.js`). Good.
- Admin routes verify a Supabase Bearer token **and** an `ADMIN_EMAIL` allowlist, failing closed if the env is unset (`lib/adminAuth.js`). Good.
- The Creatomate webhook never trusts its POST body — it re-fetches the render by id and treats that as truth. Good.
- `studio_*` tables have RLS on with service-role-only access; all client queries are scoped by `client_id` from the signed cookie, so there's no cross-client media leakage. The new `setArrangement`, `character`, `character-qr`, and `character-sheet` endpoints all enforce session/admin. Good.

**Worth addressing:**
- **P1-7 — Weak portal passwords.** Passwords are derived as `lastname + MMDD` (see `reset_password`). That's low entropy and guessable by anyone who knows the honoree's last name and event date. The portal **token** in the URL is an unguessable UUID (so it's mostly possession-based), but combined with a guessable password this is weak for private photos. Consider letting clients set a real password, or at least a longer random one, and don't reuse the event date.
- **P1-8 — No rate limiting on `/api/portal/login`.** With low-entropy passwords, brute force is feasible for anyone who has a portal link. Add basic rate limiting / lockout (e.g., per-token attempts).
- **P2-9 — `SESSION_SECRET` falls back to the service-role key.** Works, but set a dedicated `SESSION_SECRET` so rotating one doesn't affect the other.

## 4. Correctness / holes in what we built

- **P2-10 — `setArrangement` isn't transactional.** It does N per-row updates in a loop; a mid-way failure leaves a partial order until the next save. Low impact (small N, self-heals on next arrange, and it's scoped to the client's own rows), but a Postgres function/transaction would make it atomic.
- **P2-11 — Sheet text depends on a serverless font.** `lib/characterSheet.js` renders labels via SVG `sans-serif`; this works on Vercel's runtime in my tests but if labels ever come out blank there, bundle a font. Flagged, not seen failing.
- **P2-12 — Character write-up model id.** `lib/characterProfile.js` defaults to `claude-3-5-sonnet-latest`. If your account uses different model ids, set `ANTHROPIC_MODEL`. The write-up only appears once `ANTHROPIC_API_KEY` is set — that's why your test sheet had none.
- **P2-13 — Admin "Character build" download makes a Claude call every time** (cost). Fine for now; add a cache or an on/off toggle if you download often.
- **Backward-compatibility is handled:** the portal media load, montage loader, and client list all **fall back** if `timeline_pos` / `character_name` don't exist yet — so a deploy-before-migrate can't blank the portal again (that was the cause of your "photos gone" scare; running `sql/006` fixed it, and the fallback now prevents a recurrence).

## 5. Character Builder — make it amazing & sellable

### 5a. Polish ideas (to feel like a $-worthy product)
- **In-frame guidance:** use the browser `FaceDetector`/getUserMedia to show a live "✓ good framing / move closer / more light" indicator, and a subtle auto-capture countdown when the pose is held. This is the single biggest "wow" upgrade and what separates a toy from a tool.
- **End-of-shoot review grid:** show all 12 as thumbnails before submit, with one-tap retake on any (you have the pieces; make it a dedicated screen).
- **Consistency nudges:** warn if background/lighting changed a lot between shots (even a simple average-brightness/colour check).
- **Sheet options:** cover page, PDF export in addition to PNG, and a **one-tap "copy AI prompt"** (right now the prompt is on the image + in the email; make it copyable in-app). Optional brandable header for studios.
- **Formats for buyers:** offer a "contact sheet" AND individual cropped, named files in a zip — AI tools and artists both want the singles.

### 5b. Productizing it as a standalone app
Today it's embedded in the studio portal (tied to a client token). To sell it you'd need: standalone accounts, a payment path, and the capture + labeled sheet + prompt as the paid deliverable. The capture flow, the pose set, and the sheet generator are already the hard parts and are reusable.

**Who buys it:** AI-art hobbyists, indie game/D&D character art, VTubers/streamers, cosplayers, and small studios like yours. The differentiator is real: most people don't know the *right* angles/expressions to shoot, and your guided flow + labeled reference sheet + paste-ready prompt solves exactly that.

### 5c. Pricing — honest take
Your idea was **$0.99 per download**. I looked at comparable "consistent AI character" tools and the market is almost entirely **subscriptions and credits**, not one-time $0.99: examples cited include credit systems starting ~$9.90, and subscriptions roughly **$5–$23/month** (Midjourney ~$10/mo, Ideogram Pro ~$8/mo, Leonardo from ~$10/mo, CharacterGen ~$15/mo, Adobe Firefly standalone from $4.99/mo), most with a free tier. No one-time $0.99 offerings appeared. (Source below — treat as directional, not gospel; I did not find hard app-store conversion data.)

What that implies for you:
- **$0.99 one-time is far below the category** and likely leaves money on the table, *and* it fights your unit economics: each build sheet costs you a Claude vision API call + image processing, and after an app-store 30% cut you net ~$0.70. If your cost-per-build is even ~$0.20–0.30, margin is thin and every heavy user erodes it.
- **Better shapes to consider (validate with real numbers):**
  - **Freemium:** free guided capture + a basic (unbranded, no write-up) sheet; **paid unlock ($3.99–$6.99 one-time)** for the AI write-up + high-res + PDF + singles zip. Impulse-priced but above cost.
  - **Credits:** e.g., first build free, then a small pack ($4.99 for 5 builds). Matches how the category prices and scales with your API cost.
  - **Pro/studio subscription** ($8–$15/mo) if people make many characters (game devs, streamers) or for studios who rebrand the sheet.
- **Before setting any price, model one unit:** (price × 0.70) − (Claude vision cost + processing) = margin. Pick the price so that's comfortably positive at your expected volume. I can build a tiny calculator for this if useful.
- If you want the **$0.99 impulse hook**, use it as the *entry* to a freemium ladder (cheap unlock, upsell singles/PDF/more builds), not as the whole business.
